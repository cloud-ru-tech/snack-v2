# Стиль текста — конвенции

**Область действия:** любой текст для людей в репо. В частности:

- `packages/*/docs/**/*.mdx` — пользовательская документация.
- `packages/*/README.md` — автогенерируется из MDX, поэтому правила исходят оттуда.
- JSDoc и комментарии в `packages/*/src/**/*.{ts,tsx}` — это тоже текст, который читают потребители (в IDE на hover) и контрибьюторы.
- Storybook `parameters.docs` / `argTypes.description` — то же.
- `.mdx` лендинги, плашки, подсказки в `apps/docs`.


## Принцип

Документация и комментарии — рабочий инструмент. Их читают: (а) разработчики, выбирающие компонент; (б) ревьюеры PR; (в) контрибьюторы, которые будут поддерживать код после первоначальной разработки. Жаргон, разговорные глаголы, авторские «мы», уменьшительно-ласкательные формы — всё это **сужает аудиторию** и снижает доверие к тексту. Технический текст должен звучать одинаково для джуна и сеньора, для своего и нового человека в команде, для русскоязычного читателя и для того, кто читает русский как второй язык.

## Чего избегать

### Жаргон и разговорные глаголы

Бытовые/разговорные слова в пользовательском тексте смотрятся неуместно: их интерпретация зависит от контекста и опыта читателя. Заменять нейтральными техническими эквивалентами.

| ❌ Жаргон / разговор | ✅ Нейтрально |
|---------------------|--------------|
| прогреть бандл | предзагрузить бандл / preload |
| дойдёт до компонента | перейдёт к компоненту / откроет |
| моргнул, мигнул | появится / отобразится |
| инжектор, инжектится | loader / провайдер / загрузчик |
| тянет, подтягивает | загружает / запрашивает |
| падает (в смысле «ошибается») | завершается с ошибкой / выбрасывает исключение |
| отвалится | перестанет работать / упадёт с ошибкой |
| прицепить | прикрепить / привязать |
| прокинуть | передать / прокидывание → передача |
| взлетает / поднимается | запускается |
| крутится / вертится | работает / выполняется |
| залить | опубликовать / задеплоить |
| склеить, склейка | объединить / merge |
| дрова | драйвер |

### Уменьшительно-ласкательные

Сужают тон и делают текст инфантильным. Никаких «демок», «кнопочек», «плашек», «домиков», «обёрточек», «фолбэчков».

| ❌ Уменьшит. | ✅ Полно |
|--------------|---------|
| демка | demo-пример / пример / демонстрация |
| кнопочка | кнопка |
| плашка | панель / контейнер |
| обёрточка | обёртка / wrapper |
| фолбэчок | fallback / запасной вариант |
| редакторчик | редактор |
| тулзовина / тулза | инструмент / утилита |
| свг-шка | SVG / иконка |
| фронтик | фронтенд / клиент |

### Авторские «мы» и адресные «ты»

В технической документации компонент / пакет — самодостаточный артефакт, а не часть рассказа автора. Адресовать читателя напрямую (`«ты передаёшь»`) либо разделять с ним авторство (`«мы монтируем»`) — отвлекает от сути.

| ❌ Лично | ✅ Безлично |
|----------|------------|
| мы прокидываем callback в child | callback передаётся в child |
| ты передаёшь сюда значение | в этот проп передаётся значение |
| мы решили вынести utils в отдельный файл | utils вынесены в отдельный файл (без «решили») |
| тебе нужно зарегистрировать провайдер | провайдер нужно зарегистрировать |

Допустимо «мы»/«вы», когда речь явно обращена к команде/потребителю (`«в команде используем X»`, `«вы можете передать Y»`) — но в дефолте предпочтительна безличная форма.

Императив («передай», «зарегистрируй», «оборачивай») в коротких рецептах нормален и не считается «адресацией»:

> ✅ Заверни компонент в провайдер темы; для controlled-режима передай `value` и `onChange`.

### Эмоциональная окраска

Слова «прикольный», «удобный», «классный», «легко», «просто», «нужно сказать», «бомбически» — это маркетинг, а не документация. Технический текст констатирует, не уговаривает:

| ❌ Эмоция | ✅ Факт |
|----------|---------|
| легко настроить | настраивается через `X` |
| просто передай | передать в `X` |
| удобно использовать | используется как `X` |
| мощный API | API поддерживает `A`, `B`, `C` |
| прикольная фича | поддерживает `X` |

### Англо-русский «спанглиш»

Транслитерации англоязычных терминов без необходимости — путают. Если устоявшийся термин по-русски существует — использовать его. Если нет — оставлять английский оригинал в латинице, не транслитерировать в кириллицу.

| ❌ Транслит | ✅ Англ. оригинал или русский эквивалент |
|-------------|------------------------------------------|
| дискашен | discussion / тред |
| мерж | merge |
| сабмит | submit / отправка |
| риквест | request / запрос |
| флоу | flow / поток / процесс |
| тулинг | tooling / инструменты |
| дродаун | dropdown / выпадающий список |

В сомнительных случаях — оставлять английский в латинице (`Suspense`, `lazy`, `ResizeObserver`), не заменять на кириллический транслит.

### Длинные эпитеты и «вода»

Технический текст лучше всего читается, когда каждое слово несёт информацию. Слова-наполнители убирать:

- «как известно», «как мы видим», «очевидно» → удалить;
- «в данный момент», «на текущий момент» → «сейчас» или удалить;
- «является» (где можно тире) → тире.

```md
❌ Компонент является обёрткой над нативным input'ом, которая, как известно, в данный момент поддерживает три варианта оформления.
✅ Компонент — обёртка над нативным input'ом, поддерживает три варианта оформления.
```

## Где это особенно важно

- **JSDoc** — читают в IDE на hover; жаргонное слово может быть незнакомо или ввести в заблуждение.
- **README** — первое, что видит внешний потребитель пакета. Тон документа = тон команды.
- **Sentry/CHANGELOG/Release notes** — попадают в поиск, индексируются, цитируются.
- **Имена пропсов, типов, файлов** — это часть API, разговорные/жаргонные имена в API запрещены и без отдельного правила.

## Что нормально

- Императив в инструкциях («передай», «оберни», «зарегистрируй»).
- Цитирование UI-текста или внешних API «как есть», в кавычках, даже если оно неформальное.
- Англоязычные технические термины в латинице — `Suspense`, `lazy`, `Provider`, `Promise`, `ResizeObserver`, `ref` и т.п. — это часть стека, не транслитерируется.
- Метафоры, когда они короче и точнее, чем буквальное описание (например, «прокладка» для wrapper-элемента, «барьер» для runtime-проверки) — допустимы внутри кодовых комментариев, рядом с фактической причиной. В пользовательской документации избегать.
