# Внутренняя организация компонента

**Область действия:** `packages/*/src/**/*.{ts,tsx}`. Правило действует всегда. Дополняет [package-src-structure.md](./package-src-structure.md) (раскладка файлов) и [component-api-surface.md](./component-api-surface.md) (публичный API) — здесь про **тело** компонента: обработчики, функции, общий код, нейминг.

## Принцип

Тело компонента читается сверху вниз: пропсы → производное состояние → обработчики → JSX. Логика, которая не зависит от рендера (чистые функции) или переиспользуется между компонентами (общие хелперы/стили/типы), не живёт в `.tsx` рядом с разметкой — она вынесена в отдельные модули. JSX содержит только разметку и ссылки на уже объявленные обработчики, а не инлайн-замыкания с логикой.

Эти требования — частые замечания код-ревью при миграции из `@snack-uikit/*` / `@cloud-ru/*`: легаси-код приносит инлайн-обработчики, дублированные типы и хелперы прямо в файле компонента. При портировании их приводят к канону **сразу**, не дожидаясь ревью.

## 1. Инлайн JSX-обработчики выносятся в именованные

Обработчик события в JSX — это `onClick={handleClick}`, а не `onClick={() => { … }}` с телом. Инлайн-замыкание в пропе допустимо только если оно **тривиальный проброс одного аргумента без логики** (`onChange={e => onChange?.(e.target.value)}`) и не повторяется.

Любой обработчик с условием, несколькими выражениями, или используемый в 2+ местах — выносится в `const handle<Event>` (через `useCallback`, если завязан на пропсы/состояние).

```tsx
// ❌ Плохо — логика в инлайн-замыкании
<div
  onMouseEnter={() => { if (!readOnly && !disabled) setHover(true); }}
  onMouseLeave={() => setHover(false)}
/>

// ✅ Хорошо — именованные обработчики
const handleMouseEnter = useCallback(() => {
  if (!readOnly && !disabled) setHover(true);
}, [readOnly, disabled]);
const handleMouseLeave = useCallback(() => setHover(false), []);

<div onMouseEnter={handleMouseEnter} onMouseLeave={handleMouseLeave} />
```

**Единообразие внутри файла**: если часть обработчиков уже вынесена в `const handle*`, оставлять остальные инлайн нельзя — приводи к одному стилю. Смешанный «часть вынесена, часть инлайном» — это ревью-нит, который возвращают.

## 2. Чистые функции — в `utils.ts`, а не в теле компонента

Функция, которая **не использует** хуки, пропсы, состояние или замыкание компонента (детерминированно зависит только от аргументов) — выносится в `utils.ts` рядом с компонентом (`packages/<pkg>/src/components/<Name>/utils.ts`). В `.tsx` остаются только обработчики и производные значения, завязанные на render-scope.

Признак «функцию пора вынести»: её можно объявить вне компонента без потери смысла (`function clamp(v, min, max)`, `function parseMask(s, mode)`, `function extractLabel(item)`).

```tsx
// ❌ Плохо — чистая функция объявлена внутри/рядом с компонентом в .tsx
function FieldStepper(props) {
  const clamp = (v: number) => Math.min(max, Math.max(min, v)); // зависит только от аргумента + min/max
  // …
}

// ✅ Хорошо — в utils.ts
// utils.ts
export const clamp = (v: number, min: number, max: number) => Math.min(max, Math.max(min, v));
```

Если функция завязана на min/max из пропсов — либо принимай их аргументами и выноси, либо оставляй как `useCallback`. Не оставляй её «голой стрелкой» в теле.

## 3. Общее между компонентами пакета — в `shared/`, не импорт из соседа

Если компонент `B` импортирует утилиты/стили/типы/хелпер-компоненты из компонента `A` того же пакета (`import { getAcrylicProps } from '../FieldText'`) — это сигнал, что код **общий** и должен жить уровнем выше, в `packages/<pkg>/src/components/shared/` (или `src/shared/`), откуда его импортируют **оба**.

Импорт «кучи всего» из соседнего компонента-пира запрещён: он создаёт скрытую зависимость `B → A`, ломающуюся при рефакторинге `A`.

```ts
// ❌ Плохо — FieldColor тянет внутренности FieldText
import { getAcrylicProps, copyTextToClipboard, useCopyButton } from '../FieldText';

// ✅ Хорошо — общее вынесено в shared/, импортят оба
import { getAcrylicProps, copyTextToClipboard, useCopyButton } from '../shared';
```

Что выносить в `shared/`: общие хуки (`hooks/`), чистые утилиты (`utils/` или `utils.ts`), общие хелпер-компоненты (`helperComponents/`), общие стили (`styles.module.scss`), общие типы. Что оставлять в компоненте: то, что специфично только для него.

## 4. Нейминг модулей: `utils.ts`, не `helpers.ts`

В пакете — **одно** имя для модуля чистых функций: `utils.ts`. Не заводи параллельно `helpers.ts` и `utils.ts` с неотличимой семантикой. Если функций много и они разнородны — разворачивай `utils/` в папку с тематическими файлами (`utils/convert.ts`, `utils/validate.ts`), а не плоди `helpers.ts` рядом.

Исключение — тестовая обвязка `__test__/<Component>/helpers.ts` (StoryRef-объекты, `buildStoryOptions`): это устоявшееся имя из [e2e-testing-standard.md](./e2e-testing-standard.md), не путать с `src`-уровнем.

## 5. Переиспользование типов вместо дублирования

Если ось/значение уже типизировано в пакете (`Size` в `FieldDecorator`, `DateRangeValue` в `FieldDate/types.ts`, `SliderValue`) — переиспользуй этот тип, не объявляй локальную копию `'s' | 'm' | 'l'`. Производные значения (`Date | undefined`, `number | number[]`) с 2+ употреблениями выносятся в именованный тип в `types.ts`.

```ts
// ❌ Плохо — Size продублирован инлайн
type FieldDateProps = { size?: 's' | 'm' | 'l' };

// ✅ Хорошо — переиспользуем тип из FieldDecorator
import { Size } from '../FieldDecorator';
type FieldDateProps = { size?: Size };
```

Связано с [component-api-surface.md](./component-api-surface.md) (оси через `constants.ts` + `ValueOf`).

## 6. Никаких легаси-TODO без тикета

TODO/FIXME, унаследованные из снэка при миграции, не переносятся «как есть». Каждый: либо разрешается в этом же портировании, либо заменяется на осмысленный коммент с причиной и (если это кросс-пакетный блокер) пометкой фазы/тикета. «Голый» `// TODO: …` без тикета запрещён — см. [dont-do-that.md](./dont-do-that.md).

Допустимо: задокументированный cross-package блокер с явным маркером (`// TODO Phase 5 token missing: …`) — он несёт информацию о реальном ограничении, а не «надо бы потом».

## Чек-лист перед коммитом тела компонента

- [ ] В JSX нет инлайн-обработчиков с логикой/условиями — всё в `const handle*` (`useCallback` при зависимости от render-scope). Стиль единый по файлу.
- [ ] Чистые функции (без хуков/пропсов/состояния) — в `utils.ts`, а не «голыми стрелками» в `.tsx`.
- [ ] Нет импортов внутренностей из соседнего компонента-пира — общее живёт в `shared/`.
- [ ] Модуль чистых функций называется `utils.ts` (или папка `utils/`), не `helpers.ts` (на `src`-уровне).
- [ ] Типы осей/значений переиспользуются, не продублированы инлайн-литералами.
- [ ] Нет голых легаси-TODO без тикета/маркера фазы.
